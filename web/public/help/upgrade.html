    任务 08文档核对 · 2026-10-21

    更新网页与版本边界

    本页区分两类变更：本次 r11 只更新 Web；已有 rc.6→r10 的核心/schema 升级另有经过守卫的配套配置。普通验收人员先读人工验收步骤，以下替换由获准的设备管理员在原项目完成。

    本页目录
    • 本次 Web 更新前
    • 在原项目更新 Web
    • 只回退 Web
    • 核心 schema 升级另行处理

    本次 Web 更新前

    1. 核对新 Web 包 manifest：兼容核心为 lantai:v0.1.0-r10-candidate-3ad86ea10830，image ID 为 sha256:38d2114be464e0ba333f2bf4b0a3e88cfbd41bed5b474728e2513df644034945。源环境不是该兼容组合时先停止，不能因帮助显示 r11 就推定核心已升级。
    2. 私下保留原 Web 完整目录、当前静态 bind 来源、原 Compose/环境、网关配置与原 HTTPS 地址。原 r10 Web 归档 SHA-256 为 0c21322ab7506562dc0dc32e53c63b51aef6fd48184a93127ca9f3fd40707dfd；以自己实际保留的清单为准，不覆盖旧目录。
    3. 核对当前实例可登录、固定版本可读；只在批准窗口更新。此 Web 包不包含核心镜像、schema 迁移或真实配置，不改变数据/秘密卷、项目名、TLS、端口或授权。

    在原项目更新 Web

    1. 从正式交接的候选 artifact 下载 Web 包，核对 ZIP、内部 Web 归档及 manifest/SHA256SUMS；不要从任意 main 源码目录替代产物。
    2. 用文件管理界面把 *-web.tar.gz 解到新的独立静态目录，得到 web/index.html、web/assets/ 和 web/help/；核对是完整同一包，不只复制 index.html。
    3. 保留旧静态目录。在原项目把原 Web bind 的宿主来源切到新解出的 web 目录，容器目标仍为 /srv/lantai-web:ro；若原配置固定使用项目目录中的 web，则先保留完整旧目录，再整体替换该目录。遵循原有 create_host_path:false，不挂源码根、数据或秘密卷。
    4. 只在需要时重新创建或重启原 gateway 使静态挂载生效；不更换 core/prepare 镜像，不运行 migrate/init，不新建项目、卷、端口或网关 catch-all。
    5. 在浏览器重新加载，确认侧栏“首页”“我的项目”在上面，“使用帮助”能打开新“人工验收”。按合成用例检查原会话、已知固定版本与帮助返回同一站点；保留本次 manifest 和实际结果。浏览器缓存未更新时先核对版本化资源和实际挂载，不重装核心。

    只回退 Web

    若本次导航或帮助更新异常，保留新包和错误证据，把同一个 Web bind 恢复为更新前保留的完整旧 Web 目录，再按原项目方式使 gateway 挂载生效并重载浏览器。核心、schema 和卷保持原状态；这只是同一 r10 核心上的网页文件回退，不是数据库或业务操作回滚，也不会撤销已提交资料或权限变更。

    若没有可核对的旧 Web，先停止替换并补齐交接文件；不能混用两套 assets/help。

    核心 schema 升级另行处理

    已验证的 rc.6→r10 合成路径先核验完整旧保护点，再由受限、无网络的 schema-migrate 服务执行14→15，核心等待它成功。缺备份、身份/代际不符或迁移失败时拒绝启动，不能绕过依赖或删除版本记录。配套原配置说明见已验证迁移配置，这里只提供阅读入口，不在本次 Web 更新中执行它。

    旧核心拒绝 schema15，不能同卷换旧镜像降级。 独立旧格式恢复仍要管理员因素恢复、绑定证据的 restore-complete 及恢复目标自己的配置；NAS 纯 GUI 旧版恢复尚未验证。完整包生成、独立卷恢复与 NAS GUI 支持是不同事项，见恢复验收的边界。
