# 新目标恢复控制

本分支的 `start` 在新目标进入建库前提供 `/setup/`，由 T08 生命周期和 T01 身份共同所有。接口不是普通管理员或 Agent API：每步需要新目标既有的安装认领码、精确 Host/Origin、同源静态资源和禁止缓存。已初始化实例不能进入该路径。引导码来自新目标安装，不是独立恢复口令，不需要长期保存。

所有请求都拒绝 query、歧义认证头和跨 Origin。认证通过后只访问固定的私有控制目录，不接受客户端选择宿主路径。GET页面不包含秘密。控制文件记录阶段、目标绑定和已验证包摘要，不包含旧主密钥或用户口令。

| 路由 | 输入/结果 |
|---|---|
| `GET /setup/recovery/status` | 返回阶段、已上传包摘要、恢复run、新管理员标识及检查摘要。 |
| `POST /setup/recovery/upload` | `application/octet-stream` 原始包；有界长度、私有暂存、完整性校验后原子发布。 |
| `POST /setup/recovery/restore` | 精确 `package_sha256`、`confirm_new_target: true`；后台执行，返回accepted。 |
| `POST /setup/recovery/cancel` | 仅请求取消；实际worker退出前不会释放其持有的资源。 |
| `POST /setup/recovery/admin` | 原管理员用户名和新的登录口令；返回新TOTP和预先生成的登录恢复码。 |
| `POST /setup/recovery/admin-confirm` | 新TOTP及登录恢复码已保存确认；不复用旧登录。 |
| `POST /setup/recovery/review` | 执行core检查，生成绑定run/包的检查ID，单独列出捕获后未知事项。 |
| `POST /setup/recovery/complete` | 检查ID、已知变更核对、接受恢复点、原实例已隔离及启动确认；再执行领域检查后解除恢复门禁。 |

恢复材料仅在内存中交给既有身份恢复实现。完整旧身份、会话、TOTP、机器凭据、人类批准和内容授权失效；使用新运行主密钥，不沿用旧密钥作为新实例运行密钥。恢复保留原配额、上传/传输/HTTP 限制、生命周期批量参数及业务配置资产；仅用新目标配置重绑定监听、Origin、密钥目录和 FUSE 准入。后台清理调度强制关闭，不采用包里的旧宿主路径或监听配置。

旧 `lantai.recovery-review/v1` 表示明确的本机对账，保持原约束。新向导产生 `lantai.recovery-review/v2` 的恢复点接受记录：四库/身份/文件/索引检查仍必需，但捕获后未知事项保留为未知，不把三个 `*_reconciled` 伪写为true。界面要求操作者处理已知变更、明确选择该恢复点，并确认没有双机同时写入。core无法证明断开原设备上未观察到的事实。

中断后保持同一个包和恢复run。管理员秘密只存内存；若确认前重启，需要重新登记。确认已提交而响应丢失时，根据绑定该run的身份记录识别已完成确认。完成前不提供常规业务监听或发放普通会话。恢复前的安装认领能力在完成后失效，正常登录使用新管理员身份。

完整包具有敏感恢复能力：接收者能读取全部数据和所含恢复材料。内置摘要提供完整性检查，不证明独立来源；不能用包内自带公钥为包自身建立可信来源。下载文件需由使用者按私密资料保管，已复制副本不能远程撤回。
