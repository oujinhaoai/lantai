# 0002 公共契约：标识、规范化、幂等回执与锁顺序

状态：已采纳（2026-09-27）。规则全文见[公共契约](../contracts/README.md)。

## 背景

各模块需要同一套 ID、摘要、请求幂等、事件与所有权规则才能并行开发；这些规则影响持久数据，一旦分叉很难迁移。

## 决定

1. ID 为服务端生成的 ULID，只接受大写规范形式；子操作 ID 由父 ID 与稳定步骤键确定性派生，仍是合法 ULID。
2. 需要求摘要的 JSON 按 RFC 8785 规范化，输入按 I-JSON 严格解析；整数字面量限制在 ±(2^53−1)。YAML 先按 JSON 数据模型解释，拒绝锚点、别名与非字符串键。
3. `request_hash` 覆盖命令类型、项目、路径目标、预期修订、输入版本与领域规范化后的命令体，不覆盖传输细节；规则以 `lantai.request-hash/v1` 版本化。
4. 回执、operations、outbox 在业务所属库中与业务变更同事务提交，由共享组件写入并按 `owner_module` 归属；没有全局回执库。无效请求不占幂等键，已接受的业务失败有终态回执。
5. 操作阶段以 committed 为可见点；`projected` 只在对外视图中由 outbox 投递情况推导，不写入数据库。
6. 单进程锁顺序为维护屏障 → security_guard → project/namespace → asset → task/attempt → blob。blob 层是本决定新增的：GC 按哈希协调，排在最后可避免与持有资源锁的提交死锁。
7. schema 的 `$id` 以仓库原始文件地址为前缀，但校验只从内嵌文件解析，不访问网络；每个文档 schema 都有正反例并在测试中逐一核对。
8. 事件信封的 `project_id` 对实例级事件（身份、实例运维）可省略；这类事件只对有实例级读取权的调用者可见。

## 后果

- T02 与 T03 通过 `install`、`commit` 接口与内存桩各自开发；真实实现必须通过同一契约套件。
- 修改上述规则需要新契约版本或新的决策记录；历史摘要与回执不重写。
