# 0006 身份、会话、委托与人类授权的实现取舍

状态：已采纳（2026-09-27）。规则全文见[身份与授权](../contracts/identity.md)，动作矩阵见[登记表](../contracts/identity-actions.md)。

## 背景

T01 需要把“人和 Agent 都是身份、能做什么由角色决定、哪些必须由人做由策略与人在场证明决定”落到可测试的实现，并满足撤权与最终接受的串行化、TOTP 不可重放、受限恢复与凭据不泄露等验收。

## 决定

1. 长期凭据与会话令牌都是 32 字节随机数，库里只存 SHA-256；长期凭据只能换会话，不能直接调用业务接口，也不发给人。
2. 会话运行记录在 runtime.db，是否有效每次对照 main.db 的主体状态、`auth_epoch`、凭据吊销与管理员吊销记录，以及实例 `recovery_epoch` 判定，不使用缓存；管理员吊销会话的权威记录写在 main.db，与命令回执同事务。
3. 会话范围（`read`、`ingest`、`organize`、`task`、`node`、`worker`、`runner`、`service`、`admin`、`self`、`recovery`）只收窄，权限仍由角色矩阵决定；能力标签不参与授权。动作登记是权限矩阵的唯一来源，其他模块的最终接受与下载检查都调用身份模块的 `Accept`/`BeginRead`。
4. 插件、adapter 等代为调用者得到的是“委托会话”：主体仍是被委托者，另记 `delegated_by`，动作与项目显式限定、最长 1 小时、不可再委托；委托会话永远不能通过“仅人本人”检查，传输档位为批量（`authz.Context.TransferClass` 对委托上下文返回批量）。
5. 人类授权沿用设计中的 Challenge → HumanGrant → 命令：挑战与授权绑定动作、目标集合摘要、`request_hash`、operation 与会话；动态码成功即推进 `last_accepted_counter`；授权与效果、回执在 main.db 同一事务核对与提交。一次性明文（新凭据、设置码）只在首次响应中返回，不写回执。
6. 一个 operation 允许多次挑战（授权过期后按同一摘要重挑战），效果只提交一次由命令回执的 operation 唯一约束保证。
7. 口令用 Argon2id（x/crypto），参数随记录保存、并发计算数受限；TOTP 种子用标准库 AES-256-GCM 以主密钥加密，附加数据绑定因子与主体；CSRF 令牌由主密钥经 HKDF 派生的子密钥对会话 ID 做 HMAC，不存储。
8. 初始化与离线恢复只在持有数据根锁、从未开放服务的本机进程中执行；恢复码与设置码都进入受限会话，只能设置口令与登记新因子。
9. 认证失败分两组限速：未认证入口（登录、恢复码、设置码）与已认证会话内的人类授权兑换。匿名者刷满登录限速不能锁住管理员用已有会话兑换挑战；未认证入口在慢口令校验之前预记失败，并发尝试逐次计数；慢口令校验不在任何锁内进行。
10. 子会话只给 Agent 等非人主体（交给子 Agent 或子进程）；人的会话不能派生子令牌，子会话、委托会话与恢复会话都不能通过仅人本人的检查或申请人类授权。

## 后果

- REST/CLI 接线（T07）只做输入输出适配，不重复权限判断；M2 的资源审定、解锁、清除与批次授权沿用同一机制新增动作与命令。
- 撤权类写入持 `security_guard` 写锁，会与业务提交串行；它们都很少，代价可接受。
- 主密钥丢失意味着已登记的验证器无法校验，只能走恢复；主密钥须与数据根分开备份。
