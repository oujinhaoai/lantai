# 事件收录、事务消费与审计

本篇说明 M1 的内部实现边界。事件信封仍以 [公共契约](README.md#事件信封与-outbox)及 [schema](../../schemas/common/v1/event-envelope.schema.json) 为准；这里不另定义 HTTP 协议。实现位于 [`internal/events`](../../internal/events)。公开任务基线见 [T04](../tasks/T04-events-query.md)，实际进度与执行证据维护在知识库。

## 收录与内部重放

业务库在本库事务提交结果、回执与 outbox。源所有者通过 `Source.Name/Pull/Ack` 提供适配；`Store.Relay` 每次有界地执行 `pull → Collect → ack`，不会在业务提交内等待索引。收录器只操作 events.db，不借用源库事务或修改源业务表。

`Collect` 校验源信封的规范化字节与身份，按 `event_id` 唯一收录。相同 ID、相同摘要的重放不产生新事件；相同 ID、不同内容拒绝整批写入。源确认失败后持久化退避，重启仍从未确认的 outbox 重读。收录已提交、源尚未确认时退出，只会再次尝试相同逻辑事件。

`global_seq` 仅表示 events.db 收录顺序。对象业务顺序以 `aggregate_revision`、因果引用与所属模块的权威状态为准；跨源事件发生时间不构成全局事务顺序。

`Store.Read(ctx, after, limit)` 在库快照内返回 `Page{Entries, HighWater}`，`limit` 为 1–1000。`HighWater` 是这页已扫描水位，授权层过滤全部记录后仍须返回它；不能把“没有可见事件”当成“没有扫描”。该方法是受信任的内部读取，不包含用户授权，也没有公开路由或长轮询。

裁剪水位之前的任何游标（包括 0）返回 `CURSOR_EXPIRED`。重同步顺序固定为：捕获 `S = HighWater` → 扫描权威、按当前权限全量替换对应可见范围 → 从 S 重放。替换必须移除已删除或已撤权的旧缓存对象。若扫描期间 S 也已过期，则重新开始，不能继续拼接旧缓存。精确引用读取与命令接受不依赖事件索引就绪。

## 消费与跨模块后续命令

消费者所属库安装 `ConsumerSchemaSQL`，包含 `processed_events`、`consumer_offsets`、`consumer_failures` 和 `pending_commands`。这些是按 `consumer` 分区的基础设施表；消费者业务表仍只有其所属模块写入。

`Consumer.Apply` 的同一事务包含：本地状态变化、后续命令意图、事件去重记录与消费水位。业务处理器或意图校验失败时事务回滚，随后独立保存失败分类和重试时间；数据库等基础设施故障直接返回错误，不提前推进水位。`Consumer.Consume` 每次处理一个有界页，遇到第一条失败即停，不启动后台 goroutine。

| 失败类别 | 行为 |
|---|---|
| `transient` | 持久指数退避，从 1 秒增加至最多 5 分钟 |
| `missing_prerequisite` | 保持水位并退避，处理器下次对照权威 revision/前置事实 |
| `schema_incompatible` | 持久阻塞，修复兼容性后显式 `Retry` |
| `business_conflict` | 持久阻塞，完成业务处置后显式 `Retry` |

处理器不能在 SQL 事务中调用外部领域接口。它返回 `Command` 意图，由消费事务写入 `pending_commands`；子 operation ID 从父 operation、消费者、event ID 和稳定步骤键派生，执行前已持久化。消费水位前进表示意图已可靠保存，不表示下游动作已成功。

`Dispatch` 在事务和本地屏障锁外调用目标领域接口；目标重新验证当前权限、版本与修订，并按持久 operation ID 幂等接受。结果不明时目标适配器必须先查原回执对账。目标成功后保存本地回执；目标已提交但响应或本地回执丢失时，重试仍使用相同 ID 和内容。该适配仅处理事件引出的待执行命令，不建立 Task/Seat/Attempt、任务租约或通用作业调度器。

## 审计与热窗口

`ExportAudit` 输出 `events.jsonl` 和 `manifest.json`。每行包括全局收录序号、收录时间和原信封；清单记录字节数、SHA-256 摘要、逻辑水位及物理行数。提交顺序为：追加并刷新审计文件 → 原子安装并刷新摘要清单 → 更新 events.db 的审计水位和文件登记。

进程首次导出（包括每次启动后）逐行核对 event ID、摘要、序号和收录时间。重复物理行按 event ID 识别，不计为新的逻辑事件；不完整末行截断后从热库重放。已完成的中间行损坏、序号缺口或已裁剪历史缺失会明确失败，不伪造恢复。同一进程内后续批次先重算整文件摘要：与本进程上次成功导出的摘要和大小一致时直接续写，不再逐行解析与查库；不一致（文件被改动、上次导出失败）时回到逐行完整核对。每批仍顺序读取整个文件计算摘要（续写前与写入后各一次），读取量随文件大小线性增长，只是远低于逐行核对的代价。当前 M1 使用单个追加文件，尚未实现分段归档、压缩或异地审计存储。

`Prune` 的热窗口目标为收录后 90 天，避免延迟交付的旧事件刚进入 events.db 就被清除。实际仅裁剪以下限制共同允许的连续前缀：

- 已刷新到审计文件并持久确认的水位。
- 所有登记为 `required` 的消费者已提交水位。
- T08 明确报告的已验证备份水位。
- 已超过 90 天热窗口。

裁剪保留 event ID、摘要与收录序号，防止很晚抵达的重复 outbox 复活为新事件。热信封删除不影响收录高水位。关键消费者先 `RegisterConsumer`，事务成功且释放写锁后再 `AcknowledgeConsumer`；漏报只会保守地保留历史。

`ConfirmBackup` 仅固定 T08 的确认接口，不执行或证明真实备份。默认备份水位为 0，未确认备份前不会裁剪任何事件。M1 的合成水位测试不能替代备份恢复验收。

## 维护屏障与验证

`New(db, clock, gate)` 和 `NewConsumer` 接收实例共享的 `commands.Gate`。未配置 Gate 的 Store 只允许读取；收录、源确认、消费、待执行命令状态、审计和裁剪写步骤必须分别进入实例维护屏障。跨模块调用前释放本地事务和屏障，由目标独立取得其写入口，避免反向嵌套取锁。

`Metrics`、`Consumer.Metrics` 只输出水位、滞后和失败数量，供 T08 本机运维使用；源 outbox 积压仍通过源所有者的适配查询。不创建公网诊断端口。

验证命令：`go test -race ./internal/events`。测试覆盖收录后确认失败与重启、并发重复、内容冲突整批回滚、消费者事务回滚与失败分类、待执行命令响应/回执丢失、维护拒写、审计文件已刷新但 DB 水位未提交、重复物理行与截断末行、摘要损坏、联合水位裁剪、裁剪后的重复去重及过期游标。
